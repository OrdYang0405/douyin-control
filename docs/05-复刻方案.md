# 复刻方案（捷径优先）

目标：把「星辰语音」这套东西变成自己的，**能复用的一个字节都不重写**。

---

## 0. 一句话

三个部件里，**两个直接用他们的**（桌面采集端、接口契约），只自己写「后端 + 控制台 + 语音路由」，工作量从「重写一个系统」压到「实现 12 个接口 + 一个页面」。

---

## 1. 复用地图

| 部件 | 原系统 | 本地方案 | 实际工作量 |
|---|---|---|---|
| 弹幕采集 | Electron 客户端 + 13 平台 DOM 规则 + 反检测 | **原样复用**，只改 `platforms.json` 回调地址 | 0（一条命令重打包） |
| 接口契约 | PHP `api/v1.<c>/<a>` | 照抄路径与字段实现 | 小（12 个端点） |
| 控制台 UI | uni-app 三端（minified） | 自写单页（更好控） | 小（1 个 html） |
| 语音 | 云端 TTS + 声音克隆 | 双通道：云端 Edge / 本机 SAPI | 小（已跑通） |
| 虚拟声卡 | VB-Audio 封装 | 直接装 VB-Cable（官方免驱版） | 0 |
| 弹幕直连（无客户端） | App 内 `aiobs SignWss` | 已有 ApiKey，可后接 | 中（protobuf 解码） |
| 计费/卡密 | `charge*/cardToUser` | 本地分钟数 + 卡密表（已内置结构） | 小 |

**捷径的实质**：他们的客户端只做一件事——抓弹幕然后 POST 到 `socket/index/bullet`，字段就 6 个。所以「换后端」不需要改客户端，改一个 JSON 就行。

## 3. 三步跑起来

```powershell
# 1) 起服务（首次会自动重打包客户端）
pwsh -File start.ps1 -Client

# 或者分开：
pwsh -File start.ps1                 # 只起服务，打开 http://127.0.0.1:8080
```

2. 浏览器打开 `http://127.0.0.1:8080`，用 `admin / admin123` 登录 → 新增一个直播位 → 复制它的 `live_id`

3. 双击 `build\client\星辰弹幕助手.exe`，填入 **直播间地址**（抖音直播间链接）+ **回调直播位ID**（刚复制的 `live_id`）→ 开始监听

弹幕会立刻出现在控制台右侧；命中关键词的弹幕会自动合成语音并在浏览器播放。

### 让直播伴侣"听到"

```
浏览器播放语音  →  系统播放设备设为 VB-Cable Input
                →  直播伴侣麦克风选 VB-Cable Output
```
或最简单：直播伴侣里把麦克风设成「立体声混音」，把系统声一起采集。

## 8. 关键副产品：他们的更新通道是敞开的

客户端启动时会自动检查更新，日志里直接把服务端清单打了出来：

```
GET http://live.xc58.icu/output/dm-update/manifest.json   → version 28, 29 个文件
GET .../manifest.sig                                      → Ed25519 签名（只防篡改，不防读取）
```

所以我把 **v28 全量核心包直接下载下来了**（`captures/target/core-v28/`，逐个校验 sha256 全部 `OK`）。

里面比安装包里的版本多出 7 个文件，都是**协议层**的：

| 文件 | 作用 |
|---|---|
| `dom/protobuf-wire.js` | 极简 protobuf 解码（varint/field 解析） |
| `dom/douyin-protocol.js` | 抖音 PushFrame 协议：gzip 判定 + 聊天/进入/点赞/关注/在线人数解码 |
| `dom/douyin-merge.js` | ws 结果与 DOM 结果的去重合并（昵称打码匹配、messageId 去重） |
| `dom/live-network.js` | 用 CDP 挂到 webview，直接嗅页面自己的 WSS 帧（base64 → protobuf） |
| `dom/pdd-protocol.js` / `pdd-network.js` | 拼多多的同类实现 |
| `dom/protobuf-debug.js` | 帧调试输出 |

也就是说：**他们的"弹幕从 DOM 抓"只是兜底，主力早就是协议层**——用浏览器自己的签名连 WSS，再用 protobuf 解帧，DOM 只用来补漏。这部分代码已经被我 vendor 到 `server/vendor/` 并在 `server/douyin.mjs` 里复用（不需要客户端、不需要浏览器，直接用 App 里那个 `aiobs` ApiKey 换签名地址）。

## 10. 抖音直连协议（实测结论，可直接照抄）

### 10.1 三步拿到弹幕

```
1) 房间号：https://live.douyin.com/webcast/room/web/enter/?web_rid=<web_rid>&aid=6383...
   → data.data[0].id_str 就是数字 room_id
   （room_id 是 19 位数字，web_rid 是 11~12 位，别混）

2) 签名地址：POST https://api.aiobs.cn/Douyin/Douyin/SignWss
   { ApiKey, BrowserName, BrowserVersion, RoomId, UserUniqueId }
   → Data.WssUrl（wss://webcast*.douyin.com/webcast/im/push/v2/?...&signature=xxx）

3) 连 WSS：必须带 Cookie（ttwid）
   Cookie 从 GET https://live.douyin.com/<web_rid> 的 set-cookie 里取
```

### 10.2 握手失败的真相

抖音对不合规握手返回的是 **HTTP 200 + `Handshake-Status: 417`**，不是 4xx：

```
Handshake-Msg: http: named cookie not present
```

所以用 Node 内置 WebSocket（undici）只会看到 `unexpected response`，完全看不出原因。必须：
- 用能自定义请求头的 WS 客户端（本项目 `server/ws-client.mjs`）
- 带上 `Cookie: ttwid=...`（**这才是关键**，Origin 不是）

| 握手头组合 | 结果 |
|---|---|
| UA + Origin + Referer + Cookie | 101 ✅ |
| UA + Cookie（无 Origin） | 101 ✅ |
| UA + Origin + Referer（无 Cookie） | 200 / 417 ❌ |
| 仅 UA | 200 / 417 ❌ |

### 10.3 ack 帧（不回就拿不到后续帧）

服务端推第一批后等客户端 ack。ack 是 PushFrame：

```
PushFrame {
  field 1 seqid  = 1
  field 2 logid  = <收到的帧的 field 2>
  field 7 payloadType = "ack"
  field 8 payload = Response { field 5 internalExt = <收到的 internalExt> }
}
```

实测：只回 `logId + internalExt`（约 90 B）就足够维持推送；
把整帧消息塞进 ack（5~15 KB）也能用，但纯属浪费。`internalExt` 里带 `wss_msg_type` / `wrds_v` / `seq`，是续推游标。

### 10.4 帧与消息类型

```
PushFrame.payload（field 8）→ 若前两字节 1f 8b 则 gzip → Response
Response.messages[]（field 1）→ Common{method, msgId} + payload
  WebcastChatMessage      → 发言
  WebcastMemberMessage    → 进入（field 10 == 1）
  WebcastSocialMessage    → 关注（field 4 == 1）
  WebcastLikeMessage      → 点赞
  WebcastRoomUserSeqMessage / WebcastRoomStatsMessage → 在线人数
  WebcastRoomMessage / WebcastHotChatMessage → 房间状态/热点（可忽略）
```

实测 20 秒 141 条、18 秒 129 条，稳定不重连。

## 11. 语音引擎怎么接（含声音克隆）

`server/tts-config.json` 里的 `provider` 决定链路，控制台「语音引擎」面板可视化改：

| provider | 行为 |
|---|---|
| `auto`（默认） | 有自定义引擎就先用，失败回落 edge，再失败落 sapi |
| `openai` | 只用自定义/克隆引擎 |
| `edge` | 只用微软 Edge 朗读（免费、自然、9 个中文音色） |
| `sapi` | 只用本机 Windows 语音（断网兜底，音质一般） |

### 接克隆音色的办法

只要是 **OpenAI 兼容** 的 `POST {baseUrl}/audio/speech`，填 baseUrl + apiKey + 音色名就能用：
```jsonc
// 云服务（示例：SiliconFlow）
{ "provider": "openai",
  "openai": { "baseUrl": "https://api.siliconflow.cn/v1", "apiKey": "sk-xxx",
              "model": "FunAudioLLM/CosyVoice2-0.5B", "voice": "你克隆的音色ID" } }

// 本地零成本克隆（GPT-SoVITS 开 api 模式，默认 9880）
{ "provider": "openai",
  "openai": { "baseUrl": "http://127.0.0.1:9880", "apiKey": "",
              "model": "tts-1", "voice": "我的音色" } }
```

填完保存，控制台音色下拉会多出「自定义/克隆」分组。

### 降级保证

任何一环挂掉都不会哑场：`openai → edge → sapi` 逐级回落，全部失败才在控制台报错并写日志（`tts-error` 事件）。

## 12. 原系统的「声音克隆」到底怎么做的（从 APK 挖出来的）

这块之前一直是黑的，现在从 `app.apk` 的 `app-service.js` 里定位到了完整调用链。

### 12.1 接口清单

| 接口 | 方法 | 关键参数 | 作用 |
|---|---|---|---|
| `api/v1.live/person` | GET | `pass_id=1` | 拉取已训练音色模型列表（`model_id` / `model_name` / `pass_id`） |
| `api/v1.live/persons` | POST | `xuhao`, `myid` | 拉该直播位可用音色：`hostVoices`（主播）、`assistantVoices`（助播）、`pinci`（频率）、`customMi…` |
| `api/v1.live/kelong` | **uploadFile** | `file`（mp3/wav/m4a）+ formData | **上传音频训练克隆** |
| `api/v1.live/kelongx` | POST | `model_name`, `moxing_type`, `longaudio` | 用长音频补充训练 |
| `api/v1.live/goKelong` | POST | `txt`, `id` | 触发克隆任务 |
| `api/v1.live/changePerson` | POST | `person`, `zperson`, `task_id` | 切换主播/助播音色 |
| `api/v1.live/delPerson` | POST | `id` | 删除音色模型 |
| `api/v1.live/extPerson` | POST | 见 12.3 | **配置双人对播的完整参数** |
| `api/v1.member/chakelong` | POST | `suijiids` | 查询克隆进度（返回 `tankuang` 弹窗提示） |

### 12.2 音色体系（从代码常量还原）

```
分类 person_catelist: ["精品-训练", "精品-克隆", "经典-训练", "经典-克隆"]
模型类型 moxing_type: 2 = 最新精品音色（新增随机克隆）   1 = 经典稳定音色
性别     xingbie_type: 1 = 男    2 = 女
支持格式 fileExtname: ["mp3", "wav", "m4a"]
上传参数  thisset 里的 save=0, moremodel=moxing_type, select_type=当前分类
```

命名很直白：**「训练」= 用已有语料训出的模型，「克隆」= 用用户上传音频现场克隆的模型**，各分精品/经典两档。

### 12.3 双人对播参数（`extPerson` 的完整入参）

```js
{
  task_id, xuhao,
  hostVoice: "选中的主播音色ID,逗号分隔",
  assistantVoice: "选中的助播音色ID,逗号分隔",
  zhu_baifenbi: 30,        // 主播占比，默认 30 → 主播30% / 助播70%
  pinci: frequencyIndex,   // 插话/接话频率
  real_minute: customMinutes,
  welcome_txt, pin_welcome, real_welcome
}
```

**这是整套系统的产品核心**：不是单人朗读，而是「主播音色 + 助播音色」按比例交替 + 频率控制的对话式播报。复刻时如果只做单人 TTS，听感会差一大截。

### 12.4 复刻映射

| 原系统 | 我们的替代 |
|---|---|
| `live/kelong` 上传训练 | 接一个支持 voice cloning 的服务（GPT-SoVITS / CosyVoice / 商用 API） |
| `moxing_type` 精品/经典 | 映射到不同模型质量档 |
| `hostVoice` + `assistantVoice` + `zhu_baifenbi` | **在 `speak.mjs` 前加一层「双人调度器」**：按比例轮流选音色 |
| `pinci` 频率 | 控制插话间隔，避免抢话 |

具体到代码：现在 `speak()` 一次只出一个音色。要做双人，加一个 `pickVoice(stream)` ——按 `zhu_baifenbi` 概率返回 `hostVoice` 或 `assistantVoice`，再交给现有 `speak()`。**不需要改 TTS 层**。

### 12.5 已落地实现：`server/voice-schedule.mjs`

不是简单按概率抽，否则实测比例会偏离配置（试过：配 30% 实测 39%，配 10% 实测 25%）。最终用 **欠账补偿**（Bresenham 思路）：

```js
const expectedHost = st.total * target;      // 按目标，前 N 句本应有多少句主播
if (st.host < Math.floor(expectedHost)) role = 'host';       // 欠了就补
else if (st.host > Math.ceil(expectedHost)) role = 'assistant';
else role = Math.random() < target ? 'host' : 'assistant';
```

**实测 21 个档位全部命中（误差 ≤3%）**：

```
配置   0% → 实测   0.0%      配置  50% → 实测  50.0%      配置 100% → 实测 100.0%
配置  10% → 实测  10.0%      配置  70% → 实测  70.0%
配置  30% → 实测  30.0%      配置  90% → 实测  90.0%
```

两个额外规则：

| 规则 | 实现 | 实测 |
|---|---|---|
| 问句优先助播 | 正则命中问句时 70% 概率给助播 | 71.6% 走助播 |
| 连续同角色换人 | 连续 ≥3 句且在 25%~75% 区间才启用 | 最长连串 3~8 句 |

> 踩过的坑：换人规则不能无脑开。在 10% 场景下助播本就该连说很多句，强行换人会把实测比例抬到 25%，违背用户配置。所以换人只在中间比例启用。

端到端验证：配「主播=云希 30% / 助播=晓晓 70%」，灌 20 条弹幕（含问句），生成 18 个有效 MP3（`FF F3` 头），主/助播交替正常。

## 13. 「不死板」的真正来源（本轮最关键发现）

一开始以为是音色问题，换了音色还是死板。挖完 APK 才明白：**音色只占三成，七成是「话术层」和「节奏层」。**

### 13.1 他们有两种截然不同的说话方式

`thisset.type` 有 6 种播报模式：

| type | 名称 | 机制 |
|---|---|---|
| 1 | 半自由 | 参考话术改写 + 变量随机 |
| 3 | 助播 | 填商品描述，等弹幕回复 |
| 4 | AI + 碎片化 | AI 改写 + 碎片音频混合 |
| 5 | 全拟人 | 最高拟人度 |
| 7 | 碎音频二创 | 收集碎音频重组 |
| 2 | 关闭 | — |

### 13.2 核心：念的不是弹幕原文

APK 里运营配置项的原文说明：

> 「可根据参考话术进行改写，最终得出一段加变量之后的文案，变量之后的可以直接用于关闭模式讲解，**AI 会自动随机选择变量词去读**」

配套字段：

```
thisset.content      参考话术（不是弹幕！）
rewriteinterv        每 20 秒触发一次改写
txtArray / audioArray 待播文本队列 / 已合成音频队列
live/getReply?content=  弹幕 → 回答（服务端 AI）
live/reaudio         换一版重读
live/chahuaTxt       插话文本
```

**所以「死板」的根因是：我们在逐字复读弹幕，他们在念改写后的话术。** 这不是音色能救的。

### 13.3 节奏层：插语气词、留停顿、强制轮换

```
suiyyin_zhu / suiyyin_fu   主播/助播的「随机短语音库」（嗯、对、是的、好的呀）
suizhuinterv / suifuinterv  两套随机音各自的定时器
suitingdun                  停顿
forceTurnUntil              强制轮换窗口
isbozhu                     当前是主播还是助播在说
```

### 13.4 已落地实现：`server/speak-script.mjs`

用确定性规则 + 随机变体模拟这层，零依赖零费用：

| 能力 | 实现 |
|---|---|
| 意图识别 | 7 类正则：价格/链接/发货/质量/进入/问候/致谢 |
| 话术生成 | 每类 5~6 个句式模板，实词从词库随机取 |
| 变量替换 | `{greeting}` `{price}` `{call}` `{emotion}` 等 8 组词库 |
| 参考话术 | 填了话术就按话术讲话 + 随机变量，不念弹幕 |
| 语气词插播 | 35% 概率在句首插入「嗯/对/收到/那我来说」 |
| 句间停顿 | `pauseMs` + 0~500ms 随机抖动 |

**同一句弹幕，改造写前后对比**：

```
改造前（逐字复读，每次都一样）：
  小王说：这个多少钱

改造后（5 次全不同）：
  嗯，这位小王问价格，到手价就在购物车，说实话很划算
  小王问多少钱是吧，没问题，咱们这个价我再说一遍，一号链接第一个
  让我看看呀，价格我直接说，咱们这个价，小王你放心
  小王关心价格对不对，不骗你们不贵，下方小黄车写着呢
  对呀，直播间价格就是这样，小王自己算算
```

### 13.5 三层结构（这才是完整答案）

```
第 1 层 话术层  弹幕 → 意图识别 → 改写成人话     ← 决定「像不像人在说话」
第 2 层 节奏层  语气词 / 停顿 / 轮换 / 队列       ← 决定「有没有呼吸感」
第 3 层 音色层  克隆音色 / 双人对播比例           ← 决定「像不像真人声音」
```

只做第 3 层 = 声音好听但死板（我们之前的状态）。
只做第 1 层 = 像人但音色假。
三层齐了才接近 1:1。

### 13.6 与「1:1 复刻」的真实差距

| 维度 | 现状 | 达到 1:1 还差什么 |
|---|---|---|
| 话术改写 | 规则模板 + 词库 | 接 LLM（他们也是服务端 AI），句子更灵活 |
| 节奏 | 语气词 + 停顿 | 参考音频库（真人录的「嗯/对」拼接），比 TTS 念更真 |
| 音色 | Edge 9 音色 | **声音克隆**（GPT-SoVITS / CosyVoice），这是最后一块 |
| 双人 | 比例调度已精确 | 已达标 |

**结论**：现在「人味」有了，剩下的是「声线像不像」。要 1:1，只差克隆音色这一环。
